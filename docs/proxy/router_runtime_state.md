# Runtime inspection protocol v1

`GET /router/runtime-state?model_id=<id>` requires a proxy administrator. Repeat `model_id` for up to 100 distinct serving deployment IDs. Empty, duplicate, missing and inconsistent selectors fail as a whole; there is no partial success. The endpoint has no provider I/O, config read or database read and never changes serving state

The response protocol is `litellm.runtime-state/v1`. `boot_id`, `process_id` and `hostname` identify the responding process. `version` identifies the installed package, and `protocol_source_sha256` identifies the installed protocol module. Bind that digest to the reviewed artifact manifest and its separately verified image/source identity. Neither hostname nor version alone proves that the intended replica answered

`default_litellm_params` comes directly from the serving Router, independently of configured intent. `sdk_settings` reports the SDK's active global `drop_params` and `modify_params`. Each selected deployment is read from the actual Router model-list entry used for dispatch, with its actual ID and group name. No intended model payload, masked management response or config file substitutes for those entries

Every parameter projection contains the complete `keys`, `values` for the finite v1 inspectable parameter set, and `opaque_keys` for everything else. Credential values and all unreviewed parameter values remain opaque. A field with null or empty content remains present if it remains in the actual serving entry. Opaque does not mean absent, empty, safe, or removable. A consumer must reject unknown keys and reject any opaque field whose influence its reviewed provider profile cannot rule out; it must never coerce an opaque value into a safe value. Inspectable fields are not certified safe by this endpoint: a consumer must still validate types, allowed values, aliases and contradictory defaults, including drop lists and native output controls

This is an observation of one process, not a lock or a policy activation certificate. The consumer must inspect every selected serving process, pin deployment identity and protocol/module digest, reject unsupported/malformed/unknown responses, account for concurrent configuration writers, and recheck convergence before publishing an enforcement claim. A load-balanced URL without process enumeration cannot prove all replicas. The caller must keep credentials on its explicit reviewed origin and reject redirects

The legacy `/router/settings` response is unchanged and may still let configured values mask runtime values. It is suitable for configured intent, not enforcement proof

# Removal and recreation procedure v1

The response declares `removal_semantics: reload-or-recreate/v1`. Existing PATCH semantics are unchanged: omitted and null SDK parameters can retain their old values, and an empty string is a value, not deletion. This protocol adds no generic live delete or empty-clear operation. Refuse unsafe state until removal and convergence are independently verified

For Router global defaults, prepare a fresh process from the reviewed configuration with the unwanted defaults absent. Verify its installed artifact and runtime state before admitting it into the selected serving set. Do not assume an ignored `Router.update_settings(default_litellm_params={})` call replaced the current defaults

For deployment defaults, use this bounded recreation sequence only after obtaining a complete credential-preserving source of truth. A masked model-info response or this inspection response cannot provide that backup. If the actual stored deployment, its credentials, model-info, ID, group, ownership or source of truth cannot be established, stop and keep the policy inactive

1. Record the explicit target origin, deployment ID, intended group, current routing revision, all serving process identities, reviewed replacement payload hash and rollback payload hash. Keep the complete current and desired model payloads in access-restricted protected storage; exclude them from logs and normal artifacts. The replacement must preserve credentials, ownership, metadata and unrelated settings byte-for-byte except the explicitly reviewed fields to remove
2. Preview the exact field removals and target inventory. Confirm the inventory contains only the named deployment. Stop on drift, unknown state, a missing backup or any concurrent model/config writer. Retain the old image/config and do not activate the ceiling
3. Quiesce the affected group through the normal control plane, prevent new dispatch to it and drain its active requests, streams, callbacks and usage spools. Preserve other groups. Establish that no old or new process can dispatch the selected deployment during recreation. Do not delete an in-use deployment
4. Re-read the target and compare its revision and complete stored payload to the protected backup. Through the existing administrator `/model/delete` and `/model/new` operations, remove only that named deployment and recreate its reviewed desired payload under the explicit original identity. Never issue a broad delete, infer credentials, copy masked values, or silently retry an ambiguous result. Preserve an execution journal of request IDs, outcomes, timestamps and payload hashes without secrets
5. Reload or rotate the affected serving processes normally, then query this protocol directly on every selected process. Verify global defaults, the exact deployment ID/group, expected field keyspace and the absence of every removed field. Verify unrelated deployments, credentials and operator settings against the baseline. A successful management response alone is insufficient
6. Resume ordinary dispatch only after normal readiness, authorization, routing, streaming, callback and settlement checks pass. Activate a prospective ceiling only after its independent consumer integration and all-entrypoint release acceptance pass. A partial recreate remains quiesced; never publish success on an unverified result
7. Recovery uses the protected original payload and original credential source through the same bounded, quiesced, revision-checked procedure, then re-proves every serving process before dispatch resumes. Preserve uncertain execution state for inspection instead of repeating create/delete blindly. Image rollback cannot undo a changed shared database row, so restore any changed deployment state before selecting an old image that assumes it

This procedure authorizes no deployment, shared-state apply, service restart, provider call or charge. It defines the release operator's explicit preconditions and recovery boundary. The source change and local artifact acceptance are separate from production execution
